Written 19 November 2026. Covers 18 November 00:41 to 19 November 14:27 UTC, from the input system (PR #49) to the merged Sandbox (PR #74). Live build 4676f7d. In one paragraph: The harness from retro 1 now has a front end and a first playable space. Input is a named-action system for keyboard, mouse and two gamepads. The page boots to a loading screen with an asset manifest and preloader. It plays two intro logos, then shows a main menu over one of two random 2:1 posters and a New Game screen. Settings are saved in the browser behind one versioned store. Picking a difficulty now fades into the Sandbox, an experimental test scene: a sparse chunked tile map and a 1×2 box player that runs, jumps and crouches. It has a 2D orthographic view and a 2.5D perspective view, and a camera that follows the mouse aim with tunable sliders and smoothing. Its default map is a cube blockout of the moge3-cyberpunk mockup, built from a MoGe-3 depth projection, with three layers of city blocks behind it to test free perspective parallax. The orchestrator's daily devlog roll-over moved from a nightly task to a day-change hook.

Decisions made

DecisionDetail
Settings and sessionOne versioned browser key behind one store, which is the only code that touches storage. The session is plain frozen data ({ campaign, difficulty }), so it can later be saved or sent over the network. Difficulty has no effect yet.
Menu backgrounds 2:1 (D-128)Every menu background must be twice as wide as it is tall, so it scales correctly on desktop and phone. The source posters are square and are outpainted for now. A check and an AGENTS.md rule are on the backlog.
Day-change hookThe orchestrator's day roll-over runs from a message hook that checks the date, instead of a nightly scheduled task. It prints nothing unless the day has changed and the message is in the orchestrator thread.
Units1 world unit = 1 tile; x right, y up. Art is planned at 64 px per tile. The player is 1×2 tiles.
Camera rangeThe view is 18 to 28 tiles high, default 22, to be adjusted per area later. The scale was checked at 1:1 against the owner's mockups and matches.
Maps are temporaryThe character-grid JSON and the cells list are experiment formats only. Real maps will be very large and sparse, so the final format will be very different. The tile map is already sparse and chunked (32×32 chunks, negative coordinates allowed), and the game only asks it tileAt and isSolid.
2.5D with perspectiveDefault view: cubes for level tiles, a flat plane for the player, and a perspective camera placed so that the play plane always shows the zoom's tile height. Default FOV 50°. The 2D orthographic view stays as a mode.
Aim-follow cameraThe camera moves towards the mouse aim point. The aim point is projected through the camera at its rest position, never the actual one, so it cannot feed back. Min is a minimum radius (not a dead zone), Max a cap, and then the X and Y scales apply.
Camera smoothingThe camera's source point eases towards the head with a frame-rate-independent exponential ("smerp", half-life 0.05 s). It runs on the fixed 60 Hz tick, like everything else; there is no blending between ticks for drawing (T-089 is still deferred).
Free parallaxBackground layers are real geometry at depth. The perspective camera gives the parallax, with no layer speeds or scrolling code.
Experiment modeFor the Sandbox the owner dictates each change. Tests are kept light and there was no code review on PR #74.

The Sandbox in detail

Camera position, every frame

  1. Source eases towards the player's head (half-life 0.05 s; snaps on spawn, fall respawn and map change).
  2. Rest = source + Camera X/Y offset.
  3. Aim point = the mouse projected onto the play plane through a camera at the rest position.
  4. Shift = (aim point − actual head) × Follow; lengthened to Min along the aim direction if shorter, cut to Max if longer; then × X scale and × Y scale.
  5. Camera = rest + shift. The camera never rotates; it always looks straight along −z.

Process

  • Lanes: each change ran in its own worktree lane with a draft pull request, and was merged only on the owner's word. The Sandbox lane stayed open across about 20 change requests forwarded from the orchestrator, then merged once as a checkpoint.
  • Dev server: a local Vite server ran from the lane's worktree throughout, so each commit showed in the owner's browser on reload. Lanes used their own preview port and never touched the owner's.
  • Live check after each merge: wait for the Pages deploy, compare the published files and open the live page in the automation Chromium. The live Sandbox loaded at 4676f7d.
  • Questions before building: unclear requests were confirmed first (for example what Min and Max limit); clear ones were forwarded straight away with any defaults stated.
